# 读代码：代码基线与事实表

说明书、源代码文档和采集卡必须描述同一套代码。审查中最常见的严重问题，是说明书按 A 分支写、源代码文档却从 B 分支取，导致功能、参数、电机数量都对不上。所以先定基线，再读代码。

## 1. 确定代码基线

- 问清或查清要登记的是哪个分支、哪个提交、哪个工程目录。当前检出的分支不一定是要写的那个；仓库里常同时有多个版本的工程（如 V1/V2/V3、A3）。
- 用 `git log -1 --format='%H %ad'` 记录基线提交和日期，`git status` 确认有无未提交改动。
- 需要非当前分支的代码时，不切换分支，而是取到 Claude 的工作区再读：

  ```bash
  git archive <ref> | tar -x -C <工作区目录>
  git show <ref>:<路径>
  ```

- 基线的最后提交日期可作为“开发完成日期”的参考，但最终以申请人确认的真实日期为准。
- 基线写进 flowcharts/README.md 和交付说明；说明书正文一般不写提交号，除非用户要求。

## 2. 区分自研代码与第三方代码

- 第三方：芯片厂商库（HAL、CMSIS、LL）、RTOS（FreeRTOS、RT-Thread）、协议栈（LwIP、USB Device 库）、开源组件、npm/pip 依赖、代码生成器的输出。
- 半自动生成：STM32CubeMX、Qt Designer、ORM 迁移等生成的文件，文件头常带第三方版权声明。
- 说明书可以写“基于 FreeRTOS”“采用 LwIP 协议栈”，但功能描述的主体必须是自研代码；源代码文档和源程序量只算自研代码。`source_code_docx.py stats` 会自动排除带第三方版权或“自动生成”标记的文件，并列出排除原因。

## 3. 事实表 facts.md

在工作区写一份 `facts.md`，每条事实注明出处（文件:函数 或 宏名）。至少覆盖：

- **启动链**：入口 → 初始化顺序 → 调度器或主循环启动。嵌入式软件的典型链路是 `main()` → 时钟与外设 → 创建 RTOS 任务 → 应用初始化各步骤。
- **任务、线程与中断清单**：入口函数、优先级、触发方式或周期，以及阻塞在哪个对象上（队列、任务通知、事件组、信号量）。
- **对外接口与协议**：帧格式、校验算法、功能码或命令字、报文 ID、端口、波特率。由时钟树算出的速率要写出算式。
- **核心模块的处理流程**：输入 → 判断 → 处理 → 输出，以及超时、掉线、总线故障等异常的处理和恢复方式。
- **关键参数**：缓冲区长度、队列深度、周期、超时、重试次数、Flash 分区地址。
- **不一致与未确认事项**：注释与代码矛盾、定义了却没被引用的宏、未编译的分支（`#if 0`）、没被调用的函数。

非嵌入式软件同理，改为梳理入口、路由或页面、服务与数据库表、主要业务流程、权限与异常处理。

## 4. 表述要准确到代码证明的程度

以下几类措辞最容易超出代码能证明的范围，审查时被逐条挑出来过：

| 容易写过头的说法 | 代码通常只能证明 | 建议写法 |
|---|---|---|
| “每收到一次通知即发送一次” | 任务通知会合并，一次唤醒处理当前快照 | “任务由通知唤醒，读取当前快照后发送；连续到达的通知可能合并” |
| “写入在临界区内完成，保证数据完整一致” | 每次写入各自受保护，多次写入之间不是原子的 | “写槽接口和读取快照各自在临界区内完成” |
| “发送完成后释放缓冲” | 数据复制到底层缓冲并提交后即释放 | “提交至发送缓冲后释放；失败或超时同样释放” |
| “等待连接后开始监听” | 等待有超时，超时后继续执行 | 写出超时时间和超时后的行为 |
| “失败时回滚到另一槽” | 回滚还需要若干前提条件 | 写全前提条件（如“仍处于待确认状态且另一槽镜像有效”） |
| “通过命令 X 退出” | 某些状态下该命令到达不了处理函数 | 写清不同状态下的实际退出方式 |
| 简写函数名 `on_rx()` | 源码中的真实名称更长 | 写全名，或首次出现时注明“下文简称” |

原则：每个数字都要能在代码里找到出处；注释与代码不一致时以代码为准；代码确认不了的逻辑，在图和 README 里标“待确认”，说明书正文只写已确认的行为，待确认事项在最后的回复里列给用户。
