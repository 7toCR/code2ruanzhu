# 源代码文档（程序鉴别材料）

## 1. 要求

- 前连续 30 页和后连续 30 页，共 60 页；全部代码不足 60 页时提交全部。
- 每页不少于 50 行（最后一页除外）；页眉为“软件全称 版本号”，与申请表一致；页码连续。
- 第一页从一个文件的开头开始（C/C++ 为 `#include` 等），最后一页以完整的结尾结束（C/C++ 为 `}`）。
- 只收自研的核心功能代码：不放芯片厂商库、RTOS、协议栈、开源组件、自动生成文件；不出现 copyright、网址、其他公司名称。
- 必须与说明书取自同一代码基线；说明书描述的核心模块，应能在提交的代码里找到。
- 注释和空行的占比不宜过高（常见说法为不超过 30%）。

## 2. 生成

```bash
# 先统计，确认收录范围和源程序量
python3 <skill>/scripts/source_code_docx.py stats <自研代码目录...> --json out/源代码统计.json
# 再生成
python3 <skill>/scripts/source_code_docx.py build <自研代码目录...> --name <全称> --version V1.0 \
    -o out/<全称>_源代码.docx --pdf
python3 <skill>/scripts/check_ruanzhu.py source out/<全称>_源代码.docx --name <全称> --version V1.0 --pdf out/<全称>_源代码.pdf
```

- **目录参数**：传自研代码所在的目录（可多个），例如嵌入式工程的 `User/`、`App/`、`Common/`，而不是整个仓库根目录；脚本还会跳过 Drivers、Middlewares、CMSIS、build、test、docs 等目录（`--exclude` 可追加）。
- **第三方识别**：文件开头 60 行出现第三方版权声明或“自动生成”标记的文件默认排除，并在输出中列出原因。若某文件实为自研、只是带了公司自己的版权行，用 `--owner <公司或代码前缀>` 或 `--allow <文件>` 收录。CubeMX 生成的 main.c 等文件带厂商版权声明，默认不收录；不要删掉别人的版权声明再收录。
- **顺序**：默认入口文件（main、app、init 等）在最前，接着是其余源文件、头文件，最后放一个以 `}` 结尾的源文件。要让前 30 页覆盖说明书的主要模块时，用 `--files-from 顺序.txt` 指定顺序（每行一个路径，`#` 开头的行是注释）。
- **选材与排列**（用 `--files-from` 时）：
  - 只选与登记软件的功能直接相关的文件（说明书写到的模块），每个文件整段连续放，不截取片段。
  - 配置和宏定义可以放在前面，但要分散：每个头文件紧挨着对应的 .c，模块之间交替出现，不要把所有宏定义、配置文件集中堆在开头。
  - 提交的是整条代码流的前 30 页和后 30 页：列表开头几个文件进前 30 页，末尾几个进后 30 页，中间的文件（公共代码、上位机程序等）计入源程序量但不提交。
  - 先加 `--dry-run` 看前 30 页、后 30 页各包含哪些文件和行号范围，再调整顺序。第 31 页通常从某个文件的中间开始，这是正常的。
- **排版**：去掉空行（`--keep-blank` 保留）；制表符展开为 4 格；超出版心的长行折行（默认 `--wrap-style smart`：优先在空格、逗号、左括号处断开，续行多缩进 4 格），保证一行只占一行；每页固定 50 行（`--lines-per-page`），用段前分页保证行数；英文用等宽的 Courier New、中文用宋体，10 磅；默认每页行号从 1 开始（`--line-numbers continuous|none` 可改）。
- **去注释、压空格**：`--strip-comments` 去掉注释（C 风格跳过字符串；Python/Shell 只去整行注释，保留 `#!` 和预处理行）；`--collapse-ws` 保留行首缩进，把行内对齐用的连续空格压成一个（字符串内不动），宏定义和结构体就不会因对齐空格折行。参考件是这样处理的就照做（`--like` 会自动判断）。
- **可疑行**：含网址、邮箱、版权字样或公司名的行会列在报告里。整行是注释的可以用 `--scrub` 删除（删除内容写入报告）；代码行请人工处理或换文件。
- **报告**：`<输出名>_报告.json` 记录收录文件及顺序、每个文件在文档中的行号范围、被排除的第三方文件、首行末行、注释与空行占比、PDF 逐页行数。审查“三重匹配”时用它定位说明书模块对应的代码。

## 3. 照参考件生成（--like）

用户给了已获批的参考软著时，源代码文档照它的版式生成，不用本技能的默认版式：

```bash
python3 <skill>/scripts/source_code_docx.py build --files-from 顺序.txt x --name <全称> --version V1.0 \
    -o out/<全称>_源代码.docx --like 参考_源代码.docx --pdf
python3 <skill>/scripts/check_ruanzhu.py source out/<全称>_源代码.docx --name <全称> --version V1.0 --like 参考_源代码.docx
```

- 复制参考件的整套版式：字体字号（如宋体五号）、固定行距、页边距、页眉页脚、行号设置（如连续行号）；每页行数取参考件的实际行数（如 58 行），折行宽度取参考件最长行的显示宽度（如 72）。`--lines-per-page`、`--wrap-width` 可覆盖。
- 页眉中的参考软件名自动换成 `--name`（识别不到时用 `--like-name` 指定）；版本号不同时给出提示，在 Word 中核对。
- 参考件不含注释、行内没有对齐空格时，自动打开 `--strip-comments` 和 `--collapse-ws`（`--keep-comments`、`--no-collapse-ws` 可关闭）。
- `--pdf` 核对每页行数时，会为固定行距的源代码文档做预览字体映射（没有宋体的 Linux 上用等宽中文字体代替），页眉页脚上的孤立数字不计入行数。
- `check_ruanzhu.py source --like` 比较每页行数、段落和文字格式、页面与行号设置、最长行宽（S08）。

## 4. 同一申请人的多份软著（--sibling）

同一代码库拆成几份软著申请时（如“多关节协同控制”和“热管理监测与控制”），两份的提交页大段相同，容易被认为是重复申请或被要求补正。

```bash
python3 <skill>/scripts/source_code_docx.py build ... --sibling 已申请软著_源代码.docx --dry-run
```

- 输出提交页与对方文档的相同行占比、最长连续相同行数、第 1 页的相同占比，以及每个文件与对方的重合度。相同行超过 30%、最长连续相同超过 50 行、第 1 页相同超过一半，或提交页里有与对方 80% 以上相同的文件时给 WARN。
- 处理办法：与对方高度相同的公共文件（全局配置、外设初始化、通用驱动）挪到中间不提交的部分，前后 30 页留给本软件特有的代码；公共文件仍计入源程序量。是否避开重复、避开到什么程度，先问用户。
- `check_ruanzhu.py source --sibling` 对已生成的文档做同样的检查（S07）。

## 5. 源程序量

- 采集卡的“源程序量”填自研代码的总行数（`stats` 输出的“共 N 行”，含注释和空行），与生成源代码文档用的是同一组文件。
- 重新选材或调整收录文件后，`build` 末尾会打印新的源程序量；采集卡、采集卡填写内容和统计 JSON 都要同步（info-card.md 第 4 节）。
- 不要把第三方库算进去：既不符合事实，又会把说明书的页数要求抬到 40 页以上。
- 源程序量决定说明书的最少页数：1 万行以下 15 页，1 万行以上 20 页，10 万行以上 40 页。

## 6. 已有源代码文档的审查

用 `check_ruanzhu.py source` 检查页眉、页码、页数、每页行数、首行末行、可疑行和注释空行占比；有参考件时加 `--like`，同一申请人还有别的软著时加 `--sibling`。另外人工核对：

- 是否与说明书同一基线（看文件名、函数名、关键宏是否与说明书一致）。
- 前 30 页是否是核心功能代码，而不是大段的寄存器定义、表格数据或第三方代码。
- 页眉名称、版本号与说明书、采集卡完全一致（版本号常被写成 “V1.0” 与 “1.0” 两种）。
