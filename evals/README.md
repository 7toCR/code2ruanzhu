# ruanzhu-docs 评估方案

用于判断 Skill 的某次修改是否真的让软著材料更好，而不只是让文件看起来更完整。

只跑一个项目、每个版本一次的对比，只能说明“这次哪份产物更好”，不能说明哪个版本更稳定，更不能说明能否登记成功。

## 1. 固定条件

- 两个版本使用同一模型、同一输入、同一用户提示和同一预算，依赖（脚本、模板、mmdc、LibreOffice）完整可用。
- 每次运行记录 Skill 版本（commit）、模型、耗时、token 和运行日志。
- 旧版只用它自己的文件运行，不混入新版的参考资料。

## 2. 输入集

`evals.json` 列出 5 类用例：

| 类型 | 主要考察 |
|---|---|
| 嵌入式 C + RTOS（多分支） | 代码基线、第三方代码排除、每模块流程图 |
| 裸机小项目 | 不足 60 页时整体提交、篇幅不注水 |
| 桌面上位机 + 截图 | 软件说明书只写截图可见内容 |
| Web 后端 | 接口与数据库表格、运行环境 |
| 审查已有材料 | 结论先行、问题定位与改法、缺失材料 |

- 代码放在 `evals/inputs/<id>/`，`inputs/` 和 `runs/` 已在 `.gitignore` 中。
- 审查用例需要准备一份带已知缺陷的说明书（过期目录、缺图模块、空白封面项），并把缺陷清单记在本地，作为 expected。

## 3. 运行次数

- 每个用例、每个版本至少运行 3 次。
- 结果放在 `runs/<eval-id>/<version>/run-<n>/`，目录内保存全部产物和 `final_message.md`。

## 4. 两层评估

**结构检查（自动）**

```bash
python evals/grade_structure.py --code evals/inputs/embedded-rtos evals/runs/embedded-rtos/new/run-*
```

- 检查内容：三份材料是否齐全、`check_ruanzhu.py` 的 ERROR 数、功能章节是否都有图、说明书中的数值能否在代码中找到、采集卡是否编造申请人信息、交付说明是否提到 AI 承诺和待补材料。
- 结构检查只是门槛，不代表质量。

**质量评审（人工或模型盲评）**

- 按 `rubric.md` 的 9 个维度做成对盲评：A/B 随机命名，用模型评审时交换位置各评一次。
- 每个用例取新旧各一次运行配对，至少评 3 对。

## 5. 结论规则

**可以说“新版更好”，需要同时满足：**

- 在维度 1（代码忠实度）、2（三重匹配）、8（信息采集卡）、9（交接与诚信）上不劣于旧版。
- 在其余维度中，新版在多数用例上胜出的维度多于落败的维度。
- 结构检查通过率不低于旧版。

**汇报要求：** 按维度报告胜、平、负，以及同一版本不同次运行之间的差异；只在某一个用例上出现的差异单独说明，不外推。

## 6. 回归样例

每次修改脚本后，先用自带示例做冒烟测试（见 `CLAUDE.md`），再跑上述评估。
