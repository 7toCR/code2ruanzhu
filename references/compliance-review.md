# 审查模式：已有材料是否合规、还缺什么

用户问“说明书是否合规”“还缺哪些材料”时用本流程。目标是给出一份按严重程度排序、能直接照着改的清单，而不是泛泛的规则复述。

## 1. 盘点

- 列出交付文件夹里的全部文件，找出说明书、源代码文档、采集卡、截图、流程图源文件和用户的规则文件（如 RULE.md）。先读规则文件。
- 同一材料有多个版本时（如 说明书、说明书1、说明书2），按修改时间和内容确定最新版，以它为准审查，并提醒用户定稿后只留一份；模板副本、核查报告等非申请材料不要放在交付文件夹。
- 参考件（代理给的已获批样例）用来对照版式，不是审查对象。

## 2. 自动检查

```bash
python3 <skill>/scripts/check_ruanzhu.py design 说明书.docx --name <全称> --version V1.0 --code-lines <源程序量>
python3 <skill>/scripts/check_ruanzhu.py source 源代码.docx --name <全称> --version V1.0
python3 <skill>/scripts/check_ruanzhu.py card 采集卡.json --design 说明书.docx
```

源程序量未知时先用 `source_code_docx.py stats` 统计自研代码。用户只有 .doc 采集卡时，可先人工整理成 JSON 再检查，或直接人工核对。

### 检查项代码

| 代码 | 级别 | 含义 |
|---|---|---|
| H01 | ERROR | 页眉缺少软件全称或版本号，或与给定名称不一致 |
| H02 | ERROR | 页眉页脚中没有页码域 |
| H03 | WARN | 名称不以“软件/系统/平台”结尾 |
| H04 | WARN | 部分页面的页眉找不到软件全称（常见于首页不同或分节） |
| N01 | ERROR | 正文没有出现软件全称 |
| W01 | ERROR | 正文有“（待确认）”“TODO”“推测”等未定稿字样 |
| W02 | WARN | 正文有网址、邮箱、版权字样 |
| W03 | WARN | 正文有公司名称 |
| W04 | WARN | 正文用了第一人称 |
| D01 | WARN | 有修订痕迹或批注 |
| C01 | WARN | 封面表格有空白项（如作者、负责人） |
| C02 | WARN | 封面标题段带项目符号或编号 |
| L01 | ERROR/INFO | 正文不足 500 字 / 正文字数 |
| F01 | ERROR | 功能章节没有流程图（概述、运行要求、部署、接口等章节除外） |
| F02 | ERROR | 图号重复 |
| F03 | ERROR | 正文引用了不存在的图号 |
| F04 | WARN | 有图没有图题（编号版式） |
| P01 | ERROR | 页数低于源程序量对应的最少页数 |
| P02 | WARN | 无图页面少于 30 行（多由章节前强制分页或大图推到下一页造成） |
| P03 | INFO | 超过 60 页，提交前后各 30 页 |
| T01 | WARN/INFO | 目录页码与正文不符（差 2 页以上为 WARN，差 1 页为 INFO，可能是渲染差异） |
| T02 | WARN | 没有目录 |
| T03 | WARN | 目录条目在正文中找不到 |
| S01/S02 | WARN | 源代码首行/末行不像完整的文件开头/结尾 |
| S03 | WARN | 源代码含网址、邮箱、版权、公司名 |
| S04 | WARN/INFO | 注释+空行占比（超过 30% 为 WARN） |
| S05 | ERROR/INFO | 源代码页数（超过 60 页为 ERROR） |
| S06 | ERROR | 源代码每页不足 50 行 |
| K01–K14 | — | 采集卡：缺字段、待填项、名称、版本号、主要功能字数、字段长度、日期顺序、成立半年、源程序量、平台混用、信用代码格式、与说明书页眉一致、与统计一致 |

页数、页码、目录、每页行数依赖 LibreOffice 渲染，与 Word 可能差一两页；结论要说明这一点，必要时请用户在 Word 中核对。

## 3. 人工检查（脚本查不了的）

1. **三重匹配**：说明书描述的代码是否就是要提交的那套。确认分支和提交；抽查 5~10 个关键参数（周期、帧格式、ID、缓冲长度、阈值）在代码中的出处；核对说明书里的函数名能在代码中搜到。仓库里有多套实现时，这一项最容易出大问题。
2. **措辞强度**：按 code-facts.md 第 4 节的表格，找出超出代码证明范围的说法。
3. **模块覆盖**：代码中有、说明书却没写的主要模块（如升级、LED、配置存储），以及说明书写了、代码里找不到的功能。
4. **截图**（软件说明书）：截图是否属于本软件、平台是否混用、主界面是否截全。
5. **一致性**：名称、版本号、运行环境在说明书、源代码页眉、采集卡中完全一致；源程序量与统计相符。
6. **结构**：对照用户规则文件要求的章节（引言、需求分析、运行与部署等），列出缺失项。
7. **AI 承诺**：说明书、流程图、核查报告等是否借助 AI 生成（例如有 .mmd 流程图源文件、AI 写的核查报告）。若是，按 registration-rules.md 第 4 节如实提醒，不下结论、不出主意规避。

## 4. 缺失材料

按 registration-rules.md 第 5 节的清单逐项判断“已有 / 缺失 / 需申请人提供”。常见缺口：源代码文档、填好的采集卡、营业执照复印件、签章页与手抄承诺、合作或委托合同。

## 5. 回复格式

- 第一段给结论：主体是否可用、有几处必须改、缺哪几样材料，以及需要申请人先确认的事项（如 AI 承诺）。
- “必须改”和“建议改”分开列，每条写清位置（章节名或页码）、问题和改法。
- 缺失材料按“谁来准备”分组。
- 说明哪些结论来自脚本渲染、可能与 Word 有一两页差异；规则来源不是官方原文的要注明。
- 不在回复中大段复述规则；需要留档时，把详细报告写成文件交给用户。
